# Product Fit and Copy

## Domain Fit

Start with the user's domain, not a generic UI template.

- Operational tools need restrained information density, predictable navigation, compact controls, and fast repeated action.
- Healthcare, finance, security, government, and admin systems need careful evidence, role, audit, and error language.
- Consumer and brand sites can carry more imagery and emotion, but the first screen should still show the actual product, service, place, person, or offer.
- Games and interactive tools should open on the usable experience, not a marketing page.

## Vocabulary

Use the product's own nouns consistently. If the repo has a glossary, copy, schema terms, or existing UI labels, follow them.

- Do not vary important terms for style.
- Do not replace domain terms with generic synonyms when that weakens meaning.
- Keep status names, role names, record names, and workflow names stable.
- If data is missing, say it is missing. Do not invent source, identity, history, or verification.

## Copy

Good product copy helps the user act. It does not explain the UI like documentation.

- Labels should name the field or action.
- Empty states should explain the condition and next available action.
- Error text should tell the user what to correct or how to recover.
- Success text should confirm the completed action without overstating production guarantees.
- Demo copy must not claim real security, real delivery, verified identity, or production persistence.

Keep in-app copy short. Put detailed methodology in docs or handoff notes, not in the interface.
